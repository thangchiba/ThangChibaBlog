## Networking frameworkを自作した理由

NeoSocketは、[Jingi](/project/jingi)やmultiplayer sceneの実験から生まれました。Web開発で使っていたSpring BootやASP.NETのように、handler、service、dependency injectionで処理を整理したいと考えました。

その構成をstatefulなreal-timeアプリでも使いやすくすることが課題でした。ゲームやmetaverseのprototypeに加え、chatアプリの[Cypher](/project/cypher)でも使っています。

## Connection、packet、middleware

NeoSocketはconnection stateを保持し、packetをhandlerに振り分けます。Middlewareにはauthentication、authorization、traffic制御を追加できます。実際の方針はアプリ側で決める必要があり、middlewareがあるだけで攻撃を防げるわけではありません。

Neo-Protocolではpacketを番号と名前で識別します。Serializationの標準はMessagePackで、データ交換にはProtobufも検討しました。Binary serializationとpacket batchingで、繰り返しのmetadataや送信時のoverheadを減らします。削減量はpayloadによるため、以前の50〜90%という見積もりは、すべてのケースに当てはまる値ではありません。

Request-responseと、一方向のcommandの両方に対応しています。処理に合った通信方式を選べるようにすることが目的です。

## Handlerとservice

Handlerからserviceへ、アプリの処理を渡します。Chat handlerの構成例です。

```csharp
[NeoHandler]
public class ChatHandler
{
    [Autowired] private ChatService _chatService { get; set; }
    [HandleMethod]
    public void HandleChat(MessageDTO packet)
    {
        _chatService.HandleChat(packet);
    }
}
```

Serviceではconnectionのcontextを取得し、roomへの配信とデータの保存を行えます。

```csharp
[Service]
public class ChatService
{
    [Autowired] private IHandleContext _context { get; set; }
    [Autowired] private IChatDB _chatDB { get; set; }
    [Autowired] private ChatManager _chatManager { get; set; }

    public void HandleChat(MessageDTO message)
    {
        //Send message to all user in chatroom
        var chatRoom = _chatManager.GetUser(_context.Sender.State.IdentityId).ChatRoom;
        chatRoom.HandleChat(message);

        //Save message to database
        _chatDB.AddMessage(new MessageEntity
        {
            MessageId = Guid.NewGuid().ToString(),
            RoomName = chatRoom.RoomName,
            UserName = message.UserName,
            Content = message.Content,
            CreatedAt = DateTime.Now
        });
    }
}
```

TCP、UDP、WebSocket、HTTP、Unix socketで同じhandlerモデルを使うことを目指しています。ただし、各transportの特性はそれぞれ異なります。

## Packetの定義とclient

PacketにはIDと名前があり、MessagePackのkeyでfieldを定義します。

```csharp
[NeoPacket]
public class MessageDTO : NeoPacket
{
    [Key(0)] public string UserName { get; set; }

    [Key(1)] public string Content { get; set; }

    [Key(2)] public DateTime CreatedAt { get; set; }
}
```

Web client向けのTypeScript SDKにも、対応する定義を用意しました。

```typescript
@DNeoPacket(0, 'MessageDTO')
export class MessageDTO extends NeoPacket {
  @DKey(0)
  public UserName: string = '';
  @DKey(1)
  public Content: string = '';
  @DKey(2)
  public CreatedAt: Date = new Date();
}
```

Serverは.NET 7、Unity向けclientは.NET Standard 2.0から開発を始めました。TypeScript SDKにより、web appでもpacketを中心にした通信ができます。Stateful connectionはこうした用途に合いますが、すべてのwebsiteに必要な構成ではありません。

## Service lifetime

IoC containerにはScoped、Transient、Singletonと、NeoClientに合わせて寿命が決まるParasiticがあります。複数のimplementationがある場合にはQualifierで選択します。

```csharp
[Service]
[Scope(ServiceLifeTime.Parasitic)]
public class ConnectService : IConnectService
{
    [Autowired] private ChatManager _chatManager { get; set; }
    [Autowired] private IHandleContext _context { get; set; }
    [Autowired] private IChatDB _chatDB { get; set; }
}
```

Console applicationとしても、.NETアプリのbackground serviceとしても動かせます。

## これから改善したいこと

PrometheusとGrafana向けのmetric middlewareを実装し、Reactの監視dashboardも作り始めました。便利だからと多用していたSingletonの見直し、concurrencyとcachingの改善、APIの分かりやすさが今後の課題です。

Async programming、thread-safe collection、context switching、serialization、reflection、service lifetimeについて学ぶ機会になりました。Message queueやdistributed game serverは、今後の応用先として考えているものです。
